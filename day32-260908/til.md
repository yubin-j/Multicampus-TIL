## 랭그래프

조건에 따라 분기하면서 진행

복잡한 제어 흐름, 상태변화를 그래프 형태로 구성할 수 있도록 해주는 프레임워크이다.

랭그래프가 필요한 상황들
 - 고객 문의를 처리할 때 환불 요청은 환불 담당 흐름으로, 제품 문의는 상담 흐름으로 보내야 한다.
 - 문서를 검색했는데 답변에 필요한 내용이 부족하면 질문을 고쳐 다시 검색해야 한다. 검색이 계속 실패하면 정해진 횟수에서 중단해야 한다.
 - 결제나 메일 발송처럼 영향이 큰 작업은 실행 직전에 멈추고 사용자의 승인을 기다려야 한다.
 - 실행 중 오류가 발생하면 처음부터 다시 시작하지 않고 저장된 상태를 바탕으로 이어서 처리해야 한다.
 - Agent가 검색, 계산, 데이터 조회 중 어떤 Tool이 필요한지 판단하고 결과가 충분할 때까지 사용해야 한다.

그래프 구조이기에 중간에 필요성이 있으면 다시 처음으로 돌아가거나 다른 흐름을 타는 것과 같은 동작 흐름을 구성할 수 있다.

단점: 제어로직이 chain 밖의 조건문과 반복문으로 흩어진다. -> langsmith 추적이 힘들어진다.

## 구성 요소

state - 전체 흐름에서 공유하는 데이터

node - 각 처리 단계, python 흐름

edge - 노드간의 연결

state는 typedict를 상속받는 class로 구성

노드 함수의 패턴은 항상 동일
 1. state를 인자로 받음
 2. state에서 필요한 데이터를 꺼내서 작업 수행
 3. 업데이트할 필드를 dict로 반환 -> state를 건드는 것이 아님

graph 구성
 - 함수를 노드로 등록하고
 - start, end 노드 사이에 연결 작업 진행

## graph의 stream

llm의 stream은 아니고 상태 업데이트 노드단위로 반환하는 즉 각 노드의 처리 결과를 확인할 수 있는 것이다.

```python
stream_mode="values",
```

위 인자를 주는 것과 안 주는 것의 차이가 좀 있다. 형태와 방식이 좀 다른데..

없이 stream을 호출하면 단계별로 어떤 노드의 결과인지 알 수 있게 노드 이름과 그 안에서 변경한 데이터만 보여주고

위 인자를 values로 쓰면 state의 값이 변할 때마다 출력을 해준다. 그리고 state전체가 출력된다.

-> 즉 기본은 노드의 출력 결과 시점에 해당 하는 정보들만 나오고, stream_mode=values로 옵션을 주면 호출 시점부터 state에 변화가 있을 때마다 출력됨

## 정리 - Chain vs LangGraph

| | Chain | LangGraph |
| --- | --- | --- |
| 흐름 | 직선 (A → B → C) | 분기 + 루프 가능 |
| 상태 | 이전 단계 출력만 전달 | State로 전체 공유 |
| 제어 | 고정된 순서 | 조건에 따라 동적 결정 |
| 디버깅 | 각 단계 출력 확인 | 그래프 시각화 + 노드별 트레이싱 |
| 적합한 경우 | 단순 파이프라인 | 분기, 반복, 상태 관리가 필요한 경우 |
