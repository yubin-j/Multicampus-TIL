# 1부. 프롬프트 엔지니어링

## 1.1 구조화된 프롬프트

role을 지정하는 것은 **아직 유효함**.

마크다운 형식으로 작성:

```markdown
# role
# rule
# situation
# format
```

- 모델의 성능이 좋아져서 영어가 아니고 한글이어도 잘 동작함
- 위 네 가지가 유효한 효과를 발휘하더라
- 그냥 하다보니 이 키워드들이 잘 동작하던 것을 발견한 것

## 1.2 좋은 프롬프트의 4요소

| 요소 | 설명 |
|---|---|
| **역할(role)** | |
| **맥락(context)** | 어떤 상황, 어떤 배경 |
| **작업(task)** | 세세하게 작업을 지시해야 한다 |
| **형식(format)** | 마크다운, 줄글, html, json, … |

- 4개를 전부 쓸 필요는 없다.
- 하지만 **결과물을 활용하는 시스템 내에서는 필요**하다. 형식이 고정되어야 한다.

## 1.3 긴 컨텍스트의 함정

요즘 AI는 환각은 잡았다. 하지만 **내용이 긴 경우 중간 내용에 대한 추론**이 동작하는데, 그 때 조금 문제가 있을 수 있다.

## 1.4 구조화 팁 3가지

1. **구분자를 써라** — 지시와 데이터를 `#` 제목, `---`, `[]` 등으로 명확히 분리
2. **단계를 나눠라** — ex) 1단계 조사 → 2단계 분석 → 3단계 종합 → 4단계 문서화
   사람이 업무를 하는 단계와 비슷하게 지시
3. **출력 예시를 보여줘라** — 원샷, 퓨샷

## 1.5 제로샷 / 원샷 / 퓨샷

예시를 몇 개를 넣느냐에 따라 용어가 다름.

| 용어 | 예시 개수 |
|---|---|
| 제로샷 | 아무 예시가 없음 |
| 원샷 | 한 개 |
| 퓨샷 | 두 개 이상 |

## 1.6 CoT (Chain of Thought)

요즘 추론 모델은 이 과정을 내부에서 자동으로 수행.

- LLM은 토큰을 하나씩 생성하며, 생성한 토큰은 다음 예측의 입력이 된다.
- 즉 **생각 과정을 쓰게 하는 것** — 중간 계산 결과를 작업 메모리처럼 컨텍스트에 적어두게 하는 것
- 이는 요즘 모델에서는 기본적으로 적용됨. 확인이 필요하면 과정을 보이게 명시하도록 해서 볼 수 있다.
- → **자동화 설계에서는 여전히 유효한 기법**

## 1.7 Self-Consistency

여러 번의 동일한 질문을 하고 그 중 **가장 빈도가 높은 답을 채택**.

## 1.8 ReAct: Reasoning + Acting

모델이 관찰을 잘못 추론해버리면 여전히 잘못된 결과를 출력할 수 있고

요청사항 반영에 대한 부분을 보고 긍정인지 부정인지만 판별합니다.
단 음식 자체에 대한 부분과 가성비에 가중치를 더 줘서 판단해주세요.

{
	category: "",

### 프롬프트에 적용된 원리

- `# 목표` / `# analyze target` / `# rule` / `# format` → **구분자로 지시와 규칙 분리**

- JSON 스키마 고정 → **시스템에서 활용하려면 형식이 고정되어야 한다**

## 4.3 핵심 개념 — 배운 것들

### ① appendOrUpdate는 매핑한 컬럼을 무조건 덮어쓴다

처음 문제: 한 곳에서 입력이 들어오면 **나머지가 `undefined`로 리셋**.

원인 — "Values to Send"에 올려둔 컬럼은 값이 `undefined`나 빈 문자열이어도
**"빈 값으로 업데이트"로 처리**됨.

> 핵심 원칙: **건드리지 않을 컬럼은 아예 전송 목록에서 빼야 한다.**
> 매핑에 없는 컬럼은 시트에서 그대로 유지된다. (단, **update일 때만**)

해결 — 브랜치별 `Edit Fields(Set)` 노드로 필요한 키만 출력 + `Map Automatically`

```json
{
  "email": "{{ $json['이메일 주소'].trim().toLowerCase() }}",
  "hobby, food": "Y"
}
```

- `Include Other Input Fields` **꺼야** 원본 설문 필드가 안 딸려 나옴
- JSON 모드는 **Expression 토글**을 켜야 `{{ }}`가 계산됨 (Fixed면 글자 그대로 들어감)

### ④ 트리거 이벤트: rowAdded vs anyUpdate

| 이벤트 | 감지 범위 |
|---|---|
| `rowAdded` | 새 행 추가만 |
| `Row Added or Updated` (anyUpdate) | 추가 + **기존 행 수정** |

폼의 "응답 수정" 링크로 고치면 기존 행이 수정되므로, 수정 감지에는 `anyUpdate` 필요.

### ⑤ IF 통과 후에도 원본 데이터가 나오는 이유

IF의 입력이 `Get row(s) in sheet`면 `$json`은 **시트의 기존 행**.
IF는 내용을 바꾸지 않으므로 그대로 흘러감.

→ `json 변환` 노드를 **IF 뒤로** 옮기고, 참조를 트리거 노드로 바꿈

```
{{ $('hobby, food').item.json['취미'] }}
```

### ⑥ 이메일 정규화

매칭 키이므로 대소문자·공백이 다르면 **같은 사람인데 행이 두 개** 생김.

```
{{ $json['이메일 주소'].trim().toLowerCase() }}
```

### ⑦ 메일 발송과 기록의 순서

| 순서 | 실패 시 |
|---|---|
| 기록 → 메일 | Gmail 실패 시 flag는 남음 → **최초 안내를 영영 못 받음** |
| **메일 → 기록** | Sheets 실패 시 → 다음 수정 때 **한 번 더 감** (자가 복구) |

> 손실보다 중복이 낫다. → **메일 → 기록** 순서 채택

### ⑧ 아이템 참조 방식

| 표현 | 동작 |
|---|---|
| `.first()` | 항상 첫 번째 아이템 → 여러 명 흐를 때 **섞임** |
| `.item` | 짝지어진 아이템 |
| `.itemMatching($itemIndex)` | 페어링 판단이 안 될 때 |

## 4.4 경쟁 상태 (Race Condition)

### 관측된 증상

19:37:27에 두 실행이 **완전히 동시** 발생.
신규 사용자라 둘 다 **append 경로**를 탔고, 같은 행 번호를 대상으로 잡음.

| 순서 | 동작 | 결과 |
|---|---|---|
| #148 | append (hobby, food) | hobby=1, food=1, 나머지 빈 값 |
| #147 | append (name, location) | **hobby="", food=""**, name=1, location=1 |
| #149 | update (movie) | movie=1 추가 |

→ 최종적으로 취미/음식이 저장되지 않음

### 용어

- **경쟁 상태 (race condition)**
- **read-modify-write 경합** / **lost update (갱신 유실)**
- 해결 개념: **직렬화(serialization)**, **락(locking)**, **업서트(upsert)**, **멱등성(idempotency)**

`Append or Update Row`는 업서트를 시도하지만, Sheets API에 **원자성이 없어서** 이 문제가 발생.

### 채택한 해결책 — 2단 appendOrUpdate

```
[컬럼명 매칭되는 행 생성] → [생성한 행에 업데이트]
```

동일한 설정의 노드를 연속 배치. 두 번째가 **항상 update 경로**를 타므로:

- 같은 사용자끼리 겹쳐서 컬럼이 비었어도 → **다시 써서 복구** ✅
- 다른 사용자에게 행이 덮였어도 → 조회 시 없으므로 append로 **행 복구** ✅

조건 없이 항상 도는 재시도 루프인 셈.

### 다른 대안들

| 방법 | 비고 |
|---|---|
| `N8N_CONCURRENCY_PRODUCTION_LIMIT=1` | 셀프호스팅 전용. 가장 확실 |
| 브랜치별 Wait 노드 (0/15/30초) | 확률만 낮춤. 겹치면 무의미 |
| 종합 시트에 email 미리 등록 | append 자체를 없앰. **단, 폼으로 이메일을 받으므로 불가** |
| 주기적 감시 워크플로 | 중복/누락 탐지 후 알림 |

## 4.6 중복 제출 차단

같은 값으로 재제출하는 경우를 막기 위해 각 브랜치 앞단에 게이트 추가.



**변경 여부 확인** — 조건 2개, Combine `OR`, 둘 다 `is not equal to`

| Value 1 (시트 옛 값) | Value 2 (폼 새 값) |
|---|---|
| `{{ $json.hobby }}` | `{{ $('hobby, food').item.json['취미'] }}` |
| `{{ $json.food }}` | `{{ $('hobby, food').item.json['음식'] }}` |

- 신규 사용자는 조회 결과가 0건 → **Always Output Data 켜기** 필수
  (빈 아이템이 나오면 "다름"으로 판정돼 정상 통과)
- 이 게이트는 `first_sent` 상태와 무관하게 앞단에서 동작하므로,
  완료 후 동일 값 재제출도 같은 경로로 차단됨

## 4.7 테스트 시나리오

| # | 시나리오 | 기대 동작 | 결과 |
|---|---|---|---|
| 2-1 | 첫 번째 입력 | Y 기록만, 완료 메일 없음 | ✅ |
| 2-2 | 두 번째 입력 | Y 기록만, 완료 메일 없음 | ✅ |
| 2-3 | 세 번째 입력 | 최초 응답 메일 + `first_sent=Y` | ✅ |
| 2-4 | 수정했을 시 | 수정 알림 메일 (최초 메일 재발송 없음) | ✅ |

### 남은 테스트

- 신규 사용자가 3개 폼을 **1분 안에 연달아** 제출 → 행 중복 여부
- **다른 이메일 2명**이 같은 폼에 1분 안에 제출 → `.item` 페어링 확인

## 4.8 n8n 과금 참고

- **셀프호스팅** — 무료. 노드 수 무관
- **n8n Cloud** — **실행(execution) 수**로 과금. 워크플로 1회 실행 = 1 execution
  (노드가 5개든 30개든 동일)

> 노드를 늘려도 요금은 그대로. 실질적으로 늘어나는 건 **관리 비용**과
> Google Sheets API 호출량(분당 쿼터).
